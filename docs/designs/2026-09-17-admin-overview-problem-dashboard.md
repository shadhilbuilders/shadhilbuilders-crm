## The correction that shaped this

The first design doc interpreted "make admin overview like the work dashboard" literally - mirror its queue sections cross-project. The owner rejected that: **"I don't want existing cards and charts, I want something new that the admin overview dashboard [uses to] find out problems and resolve issues - when leads are not called for a long time and so on. Search it in web and create [a] day-to-day [surface] useful for admin and owner in one place."**

So the deliverable is a **problem-hunting / resolution inbox**, not a metrics report and not a queue mirror.

## Problem Statement

`/admin/overview` is the admin/owner command center. Today it is a read-only metrics page (KPI strip + three charts). It shows numbers about work. It does not surface *what is wrong and needs a human decision today*. The owner runs a team where a lead can sit uncalled for days and nobody is told; a visit can slip; a booking can stall holding money; a telecaller can go quiet - and none of that appears anywhere until the owner asks and digs per project. The owner wants one daily screen that says "these are the problems, in order, here is the fix" across every project and team.

## Demand Evidence

The owner's instruction is the demand. It names a concrete, recurring pain ("leads is not calling so long time") rather than a vanity metric. The web research that shaped the concept agrees overwhelmingly:

- **"Pipeline Exception Dashboard" flips the traditional review model on its head** - aggregate dashboards "nobody looks at twice a week are decoration"; an exception feed is a habit because it names the fixable issue. (zime.ai, top-15 sales reports)
- **"Highlight at-risk deals missing next steps" / "deal that has slipped past its expected stage duration."** (Bitrix24 real-estate CRM)
- **"Stale emails/departed contacts inflate pipeline counts and distort forecasts"** - the exception list is accurate where an aggregate chart lies. (prospeo.io)
- **"Most SLA problems are systemic, not individual"** - the owner's highest-value job is spotting *patterns* (a team going quiet, a clogged stage), which only a cross-project exception feed surfaces. (rework.com LMA)
- Follow-up cadence norms: first conversation attempts daily for 3 days, then day 7/14/21/30 - gives concrete idle-age thresholds to surface. (sayso/asksayso; saber.app SLA glossary)

## Status Quo

- `/admin/overview` shows 4 KPIs + 3 charts. No problems, no actionable rows.
- To know "which leads haven't been called," the owner must open each project, then each lead, and compare timestamps by eye.
- Nothing aggregates "what needs me today" across all teams and projects.

## Verified facts (in code, not assumed)

- **Admin/owner see ALL projects** on leads/bookings/visits lists (no role narrowing; only cross-tenant RLS) - confirmed `leads.service.ts`, `visits.service.ts`, `bookings.service.ts`. The new aggregate endpoint gets the same treatment (admin-only guard, unscoped).
- **`Lead.updatedAt` is the real, maintained "last touched" signal.** Prisma `@updatedAt` bumps on every state-transition write. The list already returns it.
- **The `Activity` table (per-lead action log) is populated by NO production code** - only tests write rows (`leads.detail.test.ts:257`). The dashboard's `avgTimeToFirstTouch` reads Activity but nothing creates it in the running app. **So "last call" must come from `Lead.updatedAt` today; Activity is the future richer source, not a current one.** The design must say so plainly and not pretend Activity is live.
- The KPI strip / chart components on `/overview` come from `useDashboardOverview` + `useDashboardStats`; both stay for their data but the page surface is rebuilt.

## Constraint

- Route stays `/[orgSlug]/admin/overview`. Admin/owner only (existing guard + redirect already gate).
- Charts and the KPI-strip-as-queue are NOT carried over - the owner rejected them.
- New content must surface **problems with a resolution action in one place**; honest numbers; real data only.

## Premises

1. The admin/owner daily surface is an exception/problem inbox, not a metrics report - agree/disagree.
2. "Leads not called / not touched" is the flagship problem type; idle-age comes from `Lead.updatedAt` (real), with Activity as a future upgrade - agree/disagree.
3. Each problem row links to the actionable surface (lead page, reassign, schedule, booking approve) so the owner resolves from the dashboard - agree/disagree.
4. A single admin-only aggregate endpoint computes all the exception buckets so the surface is accurate and cheap - agree/disagree.

## Approaches Considered

### Approach A: Admin-exception endpoint + one-page problem inbox
Add ONE admin-only GET `/api/dashboard/exceptions` that computes, under one RLS query, buckets for: idle/no-touch leads (by updatedAt age, bucketed 1/3/7/14/30 days), visit risk (unassigned/no-outcome-today), booking money stuck (token-vs-approval age), and team/exec quietness or overload. Frontend `/overview` renders cards - one per problem type, count-as-filter, each row links to the fix. Charts and old KPI strip removed.
- Effort: M (human ~2 days / CC ~3 hrs)
- Risk: Low-Med. Backend is a new read-only endpoint (additive). Frontend is a new component, not a reuse.
- Pros: Accurate; the "idle" number is real; owner resolves inline; one endpoint keeps it cheap; matches the researched exception-dashboard pattern exactly.
- Cons: New backend endpoint + its tests; more build than a frontend-only swap.
- Reuses: `withRlsContext`, admin role guard (mirror `dashboard/overview`), `useProjects()` registry for deep-link slugs, `ScheduleVisitDialog`, `BookingApprovalDialog`, `projectHref`.

### Approach B: Frontend-only exception inbox from existing lists
Derive the idle/visit/booking buckets client-side from the existing unscoped list endpoints (`useLeads`/`useVisits`/`useBookings`). No backend change.
- Effort: S (client ~3-4 hrs)
- Risk: Medio-Alto. Accurate only up to the list row fields; "idle since" from `updatedAt` is fine, but visit-age/token-age need fields the list rows may not expose; the "team quiet / overloaded" cards would be guesswork without an aggregate.
- Pros: Ships fastest, zero backend.
- Cons: Buckets are derived and can be wrong/stale; the flagship idle card needs the lead list at limit 100 (cross-project idle could be truncated); fewer problem types possible.
- Recommend against as the final, but reasonable as a first slice.

### Approach C: Two-phase - frontend now (Approach B), backend aggregate later (Approach A)
Ship the client-derived inbox first to see what the owner actually uses, then add the endpoint.
- Effort: S → M
- Risk: Med. The first version may surface the wrong idle numbers and burn trust before the real endpoint lands.
- Pros: Fast signal; owner sees the shape.
- Cons: Two passes, possible rework of the cards when the endpoint arrives.

## Recommended Approach

**Approach A**, with a note: the frontend-only slice (Approach B) is a valid first increment if speed matters, but the **flagship idle card's trust depends on a real aggregate**; Approach A is the finish line and is not much larger.

## Design detail - the surface

One page, four exception cards (each = one problem class; count as a filter; every row is a specific issue with a "resolve" link):

1. **Idle / not-touched leads** (flagship): leads out of terminal states (not WON/LOST/COLD) whose `updatedAt` is older than a threshold. Bucketed idle-age (overdue NEW beyond 30m SLA; then 1 / 3 / 7 / 14 / 30 days). Row: lead identity, owner, project, last-touch age, "Open lead" (+ "Reassign" where appropriate). Sorted oldest-first so the owner works the worst first.
2. **Visit risk**: today's visits with no assigned exec (or not yet logged an outcome past their slot); unassigned exec visits.
3. **Booking money moving**: TOKEN bookings approved-but-didn't-move / sitting in APPROVED without follow-through; HOLD bookings with no token received and their age.
4. **Team/exec health** (the systemic one): an exec/telecaller with zero `updatedAt`-touches in N days across their leads (quiet), OR a load imbalance (new leads in > handled). This card exists to surface "systemic, not individual" problems, per the research.

Deep-links resolve via `useProjects()` registry (projectId → slug) since the page is cross-project. Dialog actions (`ScheduleVisitDialog`, `BookingApprovalDialog`, reassign) open in place like the work dashboard does.

## Backend sketch

`GET /api/dashboard/exceptions` - admin/owner-only guard (mirror `dashboard/overview`'s service guard). One `withRlsContext` transaction computing the four bucket arrays with raw SQL over `Lead.updatedAt`, `SiteVisit`, `Booking`, and a staff-lead-touch aggregate. Additive, read-only, no schema change, honest empties. `Lead.updatedAt` is the single source of "last touched" (see verified facts).

## Open Questions

1. ~~Idle thresholds~~ **RESOLVED by owner (2026-09-17):** flagship idle threshold = 1-3 days without a touch; the SLA-overdue NEW (>30m) bucket is separate and ships alongside. Buckets: overdue-NEW >30m, then idle 1/2/3 days, then 7/14/30 as "long idle" escalation tiers.
2. Team-quiet / overload card: keep, or cut to the three money-adjacent cards first? It is the one card needing the most aggregate math and the least certain to be used daily.
3. Should each card limit to top-N rows (e.g. 10) with a "See all" to the relevant existing list page (leads/visits/bookings), or render everything? Default: top-N + "See all" to keep the page scannable.

## Success Criteria

- An admin/owner on `/overview` can, from one screen, see every problem worth a decision today (idle leads, visit risk, stuck money) and resolve each row inline.
- Idle numbers are real (server-computed from `updatedAt`), not client guesses.
- Charts and the old KPI strip are gone.
- The page is scannable on a phone (cards stack; rows link to actions).
- Tests green: backend exceptions-endpoint tests, existing overview tests pass, type-check + lint clean.

## Distribution Plan

Existing web deployment pipeline (web on Vercel via `vercel.yml`). Backend endpoint ships in the same merge. No new channel.

## Dependencies

- The `useProjects()` registry already exposes projectId → slug for deep-links.
- `ScheduleVisitDialog` / `BookingApprovalDialog` already open by id, no project segment needed.
- No Activity-writer work is required now (idle uses `Lead.updatedAt`); adding Activity writers is a separate, future upgrade if the owner wants a true "last CALL" signal distinct from "last edit".

## The Assignment

Before any code: the owner sits with `/admin/overview` open once, as themselves, and answers in one line each: (1) "how long without a call is 'too long' for a lead?" - that sets the flagship threshold; (2) "which one of these four problems would I actually look at every morning?" - that sets the card order and what to cut. One sit-down, two answers, and the build has its spec.
