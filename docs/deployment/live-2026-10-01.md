## Backups (added 2026-10-01, item 3)

- **What**: daily `pg_dump` of `shadhil_crm` (custom-SQL plain dump, gzip'd,
  **age-encrypted**) → `/data/coolify/shadhil/backups/`.
- **When**: systemd timer `shadhil-backup.timer` — 02:30 IST daily
  (host timezone set to Asia/Kolkata; `Persistent=true` catches missed
  runs after reboots; ±5m random delay).
- **Retention**: newest 14 dailies, plus Monday files up to 56 days.
- **Key**: `age` x25519. Private half: `/etc/age/keys/backup_key.txt`
  (VPS, 600) MIRRORED at `~/age-backup-private-key.txt` (local, 600).
  Public half: `/etc/age/keys/backup_pub.txt` (safe to store anywhere).
  Losing both copies of the private half = backups unrecoverable.
- **Integrity**: after writing, the script decrypts the artifact and
  greps for the pg_dump `complete` sentinel; failures raise a Telegram
  alert (bot config comes from secrets.env) + journald
  (`journalctl -t shadhil-backup`).
- **Offsite copy**: a Hermes cron job (`24e29faffaea`,
  "shadhil-backup-offsite-pull") runs on this WORKSTATION at 03:00
  local, scp-pulls the newest archive to `~/backups/shadhil/` (keeps
  30). Files are age-encrypted, so they are safe unencrypted-on-disk.
  NOTE: this depends on the Hermes gateway running on the workstation;
  true server-side offsite (R2/B2 lifecycle bucket) remains the
  upgrade path when credentials exist.
- **Restore drill (performed 2026-10-01, PASS)**: fresh postgres:16-alpine
  container + `age -d ... backup | gunzip | psql` restored the full
  schema. Restore runbook:
  1. Provision a fresh Postgres with `docker/postgres-init/` mounted at
     `/docker-entrypoint-initdb.d` FIRST (creates `shadhil_app`; the drill
     correctly showed the dump alone has roles it can't create).
  2. `gunzip -c <file>.sql.gz.age | age -d -i key | psql -U shadhil -d shadhil_crm`
  3. Point the stack at it (env DATABASE_URL/DIRECT_DATABASE_URL),
     restart the Coolify service.
