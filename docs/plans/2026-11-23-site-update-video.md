# Site updates: record and upload video next to photos

Status: approved by the autoplan gate (CEO, design, DX, eng) on 2026-11-23. Nothing is built yet; the ten known gaps at the end still stand, and gaps 1 to 4 block step 5. Author: PaalStack. Date: 2026-11-23.

Scope: staff capture video on the Site updates page (a villa's progress feed), the customer
portal plays it in the same timeline as photos, and the same update is delivered to the buyer over
WhatsApp. The WhatsApp leg was added after phase 1 by owner decision.

## Implementation plan

### 1. What exists today

Verified in this tree, with the corrections the Eng gate forced.

- `ProgressPhoto` (`packages/database/prisma/schema.prisma:683`) is the only row type that carries a file: `key String` (NOT NULL, `:690`), `mimeType`, `filename`, `caption`, `takenAt`, `stage`, `createdBy`. `clientDeviceHint` is a request field (`customer-progress.service.ts:60`), not a column. No size, no kind, no tombstone.
- Columns are quoted camelCase with no `@map` (`migrations/20261026160800_customer_progress_slice1/migration.sql:31-44`). Every CHECK or index added later must quote `"posterKey"`, not `poster_key`.
- Upload is `POST /api/media` base64 JSON capped at `MAX_UPLOAD_BYTES = 10MB` (`storage.limits.ts:7`); the controller ends with `res.end(data)` and understands no `Range`. Chat attachments still use this path in production (`hooks/queries/crm.ts:764-772`), so 10MB stays the chat cap.
- `sniffMime` (`storage/sniff-mime.ts`) knows the ISO-BMFF `ftyp` box and MPEG audio, then falls through to `return 'video/mp4'` for any unnamed brand (`:84-86`). QuickTime `qt  ` is therefore already labelled `video/mp4`; the existing test pins only `isom`/`mp42` (`sniff-mime.test.ts:59-60`). There is no EBML branch, so a WebM buffer returns null (`:92`).
- `StorageProvider` is Buffer in, Buffer out (`storage.provider.ts:25-54`). `read()` fetches the bare `publicUrl(key)` plus `?tr=orig-true` with no signature (`imagekit.storage.ts:83-93`), so a private object 403s through the current reader. `save()` takes no privacy or kind input.
- The BFF forwards only `Authorization` and `Content-Type` (`app/api/bff/[...path]/route.ts:99-104`), so `Range` never reaches Nest, and always builds a body (`new NextResponse(new Uint8Array(body), ...)`, `:119-130`), which is invalid for a 204.
- The stage and the counts are derived inconsistently: `unit-row.ts:54-59` pulls one newest row through a single `take: 1` relation, `:146-153` fills `lastPhotoAt` and `lastPhotoStage` from it, and `:150` counts every row through `_count.progressPhotos`. The portal page uses `photos.length` / `photos[0]` (`(portal)/portal/page.tsx:138`), and the hero renders `Not recorded` when its stage is null (`portal-hero.tsx:187-196`).
- `SiteCaptureView.tsx` accepts `image/*`, `maxFiles={8}`, 10MB, and rejects non-images (`:128-141`). The page that renders it is a client component (`site/[unitId]/page.tsx:1`), so it cannot read a server-only env flag. Playback assumes images: `portal-hero.tsx`, `photo-lightbox.tsx`, `SitePhotoViewer.tsx`.
- Errors are `{code, message, details?}` via `CodedException` (`common/errors/coded-exception.ts:22-58`); the web `ApiError` keeps `code` and `details` (`apis/client.ts:16-41`). The progress controller throws a bare `BadRequestException` (`customer-progress.controller.ts:66-72`). Neither carries a retry hint.
- WhatsApp: `OutboundMessage` is 1:1 with a chat `Message` (`outbound.service.ts:78-92`). `uploadMedia()` already uploads image, document, video and audio and returns a media id (`whatsapp/whatsapp.client.ts:358-408`), `sendMediaMessage()` already sends video (`:416-424`), and `outbound.service.ts:435-455` already reads bytes through storage and sends them. `isServiceWindowOpen` / `serviceWindowExpiry` live in `packages/api-types/src/chat.ts:133` and are used by chat (`chat/chat.service.ts:45-46`). Missing: a video template header and a delivery row.
- RLS is FORCE on this table (`prisma/rls/policies.sql:1626`) and the CRON_SERVICE arm requires both `app.user_role = 'CRON_SERVICE'` and `app.user_id = 'cron-service'` (`:775-795`). A new table without grant, enable, force and policies inserts nothing, silently.

### 2. The decision

Video lives in `ProgressPhoto` behind a `kind` discriminator, with database-level invariants. One table, not two: one timeline, one access rule, one delete path. The price is auditing every query that assumes "every row is an image", paid once.

Photo stays the one-tap primary. Video is a second target of the same size. Gallery moves to overflow.

### 3. Privacy, proven then enforced

Measured on this account on 2026-11-23 with the installed SDK, not assumed:

    isPrivateFile: true  on a 1s H.264 clip -> bare CDN URL 403, 25 bytes
    isPrivateFile: false on the same clip    -> bare CDN URL 200, video/mp4, 4659 bytes

The SDK typings call the flag "only relevant for image type files". The API honours it for video. Video is stored private; photos keep today's behaviour.

The flag alone is not a guarantee. The upload signature is HMAC-SHA1 over `token + expire` only, so `folder`, `fileName` and `isPrivateFile` come from the browser unsigned. A client can therefore upload publicly, into another folder, or repeatedly until the token expires. Enforcement moves to the server:

- The auth route issues a folder the client cannot choose: `/<organizationId>/<uploadId>/`.
- The record route asks the provider for the stored object's details and refuses unless the object is private and its path is inside that folder. A public object is deleted and the request fails with a code. No row is written.
- Reads are signed in the provider, never in the BFF. The web tier holds only the endpoint and display URL (`next.config.ts:29-41`); `ImageKitStorage` holds the private key and already builds every read URL. `read()` and `readStream()` sign there, and the browser never receives a signature.
- Signing means building the URL with `URLSearchParams`, because the current code appends `?tr=orig-true` to a string and a signed URL already carries `ik-t`/`ik-s`.

### 4. Data model

`ProgressPhoto` gains, in one migration:

- `kind Kind @default(PHOTO)`, enum `PHOTO | VIDEO`. `ADD COLUMN ... NOT NULL DEFAULT` is metadata-only on Postgres 11+, so no row rewrite and no add-nullable-then-update dance.
- `key String?`, nullable from the start so a tombstone can clear it. Every reader tolerates null: `progress-photo.mapper.ts:165`, `media-access.service.ts:59-63`, the outbound read.
- `sizeBytes Int?`, `durationMs Int?`, `posterKey String?`, `batchId String?`, `uploadId String?`, `archivedAt DateTime?`, `hasAudio Boolean @default(false)`.

Constraints, quoted camelCase:

- `@@unique([organizationId, unitId, uploadId])`.
- `@@unique([organizationId, key])`, `@@unique([organizationId, posterKey])`.
- `CHECK ("kind" <> 'VIDEO' OR ("posterKey" IS NOT NULL AND "durationMs" IS NOT NULL AND "sizeBytes" IS NOT NULL) OR "archivedAt" IS NOT NULL)`: a live video has a poster, a duration and a size; a tombstone may have neither.
- `CHECK ("durationMs" IS NULL OR "durationMs" BETWEEN 1000 AND 45000)`.
- `CHECK ("sizeBytes" IS NULL OR "sizeBytes" <= 14680064)`.

Both unique indexes are on nullable columns, which is what we want: nulls are exempt, so photos and un-postered rows never collide. Separate indexes do not stop a video's `posterKey` equalling another row's `key`; the delete path and the orphan sweep handle that case, and the plan says so rather than claiming a guarantee it does not have.

`key` going nullable is a widening change: every existing reader is audited in step 1, and `progress-photo.mapper.ts` starts returning a nullable `mediaUrl` with a tombstone state.

One derived summary, `UnitUpdateSummary`, replaces the three ad-hoc computations:

```
photoCount        count where kind = PHOTO
videoCount        count where kind = VIDEO
updateCount       count of all rows
lastPhotoAt       newest PHOTO
lastUpdateAt      newest row of any kind
lastRecordedStage stage of the newest row WHERE stage IS NOT NULL
lastStagedAt      that row's takenAt
```

`lastRecordedStage` deliberately ignores a newer clip with no stage, so "a newer stageless video moves neither the stage nor its date" is true by construction rather than by convention. `unit-row.ts` needs two filtered `take: 1` relations plus a filtered count (`_count.progressPhotos` cannot serve one count of photos and one of videos); that select is named here because it is on the hot units grid.

`lastPhotoStage` stays as a deprecated alias for `lastRecordedStage` until step 7, which is where its last reader dies. Sixteen call sites across three workspaces read it, including `packages/api-types/src/inventory.ts:73`, so removing it at step 4 would break the web typecheck before the UI exists.

### 5. Transport

**Signing.** `POST /units/:unitId/videos/upload-auth` returns a discriminated union:

```
{ transport: 'direct', publicKey, urlEndpoint, token, expire, signature, folder, maxBytes, isPrivateFile: true }
{ transport: 'inline', maxBytes }
```

600 second expiry. `folder` is server-issued: `/<organizationId>/<uploadId>/`. `StorageProvider.createUploadAuth?()` is typed, and `LocalDiskStorage` implements it with `{ transport: 'inline', maxBytes }` so the dev path exercises the same client branch.

**Reading.** One provider method, one result shape, used for sniffing and for serving:

```
stat(key): Promise<{ size: number; mimeType: string; isPrivate: boolean }>
readStream(key, range?): Promise<{ status: 200 | 206; headers: Record<string,string>; body: ReadableStream }>
```

`read()` survives for whole-file consumers, and signs for private objects. `GET /api/media/:key` streams, with `Range` passed through to the provider and `206`, `Content-Range`, `Content-Length`, `Accept-Ranges` and `ETag` preserved. A real `@Head` handler answers size from `stat` without reading bytes.

**The BFF.** For media paths only: forward `Range`, `If-Range` and `Accept` upstream, return `upstream.body` with the upstream status and end-to-end headers, and drop hop-by-hop and `Content-Encoding`. Redirects are followed **server-side** and never forwarded: a 3xx Location to a signed URL would hand the browser the thing the design hides. Null-body statuses get `null`, not an empty `Uint8Array`, because the current code's `new NextResponse(new Uint8Array(0), { status: 204 })` throws. Non-media paths keep buffering until those two fixes are tested.

### 6. Capture UI

Photo stays the one-tap action, Video is a second target, Gallery goes to overflow.

`SiteRecorder.tsx`, full-screen, explicit state machine:

```
idle -> requesting -> denied-temporary | denied-permanent | unsupported
     -> recording -> stopping -> preview -> uploading (0..100) -> saving -> done | failed
```

- **Container is forced, not hoped for.** `MediaRecorder` is constructed with `{ mimeType: 'video/mp4;codecs=avc1' }` after `MediaRecorder.isTypeSupported`. Chrome on Android defaults to WebM, which the sniffer refuses and Meta will not accept for video, so WebM is never produced. If no supported MP4 type exists, the recorder does not open; the picker path is offered instead with the same rules.
- **Audio is a visible toggle**, defaulting to off. It is a real microphone track when on, `hasAudio` is recorded, and the site route permits `microphone=(self)`. Nothing in the schema, transport or delivery forbids audio later, which is why it is a toggle and not a constant.
- 720p, 2.5 Mbps, portrait first, rear camera preferred. Track stopped on unmount, backgrounding and hardware back.
- 45 second ceiling with countdown in the last 10 and automatic stop; one clip per update, and after saving the screen returns ready for the next update, one tap away.
- Denied-permanently shows the browser's own path and falls back to the picker.
- Picker caps per kind: 8 photos, 1 video.

**Flag and permission come from the server.** The page that renders the capture screen is a client component, so it cannot read `process.env`. A server wrapper (`page.tsx`) reads `SITE_VIDEO_CAPTURE` and passes `videoEnabled`; `next.config.ts` gains the exact source `/:orgSlug/projects/:projectSlug/site/:path*` with `camera=(self), microphone=(self)`, and the same server read passes `cameraAllowed`. `getUserMedia` is called only when a take starts.

### 7. Playback

A video row renders as a tile: poster, duration, play glyph. Tapping opens the lightbox in a video state. The feed row is a single `<button>`, so no `<video>` is ever nested inside it.

`preload="none"`, `playsInline`, `poster` from `posterKey`, controls on, player created on open and torn down on close. The lightbox becomes kind-aware; the photo path is unchanged. When the browser cannot decode the clip, the lightbox says so in one sentence and offers a download link instead of a black box. The portal hero shows the newest row of any kind.

### 8. Server write path

`POST /units/:unitId/videos` records after the bytes land. Body: `key`, `posterKey`, `uploadId`, `batchId`, `caption`, `takenAt`, `phaseId`, `hasAudio`, `durationMs`, `sizeBytes`. No `mimeType`: the bytes decide.

1. Resolve unit and caller, same guard as the photo route.
2. Validate the key with the existing normaliser (`media-key-scope.ts:31-55`), which already handles the local-disk form without a leading slash, and require the path to sit inside the server-issued `/<organizationId>/<uploadId>/` folder.
3. `stat(key)` for the real size, type and privacy. Refuse a public object (`VIDEO_NOT_PRIVATE`), and delete it.
4. `readStream(key, { start: 0, end: 63 })` and sniff the header bytes. WebM and QuickTime are refused with their own codes.
5. Sniff the poster and require an image type.
6. Insert inside the tenant transaction.

`uploadId` conflict is not a failure: matching `key` and `posterKey` replays 200; differing keys return 409 and delete nothing, because those blobs may belong to the row being retried. A retryable DB failure deletes nothing either; the retry reuses them.

Cancel: `DELETE /units/:unitId/videos/pending/:uploadId`, idempotent, restricted to that server-issued folder. It exists because the browser cannot delete an ImageKit object without the private key.

`deletePhoto` is updated in the same step: it selects and deletes both keys, audits both, and tolerates a null `key` on an archived row.

### 10. Rollout

Each step is green on its own, in this order. The order is forced: signing must precede any private read, and policies must precede any new table.

1. **Schema and RLS, one migration.** `kind`, nullable `key`, `sizeBytes`, `durationMs`, `posterKey`, `batchId`, `uploadId`, `archivedAt`, `hasAudio`, the CHECKs and unique indexes; `StorageUsage` and `SiteUpdateDelivery` models with GRANT, `ENABLE` and `FORCE ROW LEVEL SECURITY`, member policies and the CRON_SERVICE claim arm; readers audited for nullable `key`; `lastPhotoStage` kept as an alias.
   Index strategy: preflight duplicate `("organizationId","key")` rows, create the unique indexes outside the migration transaction (`CREATE UNIQUE INDEX CONCURRENTLY`) and add CHECKs as `NOT VALID` then `VALIDATE CONSTRAINT`, because a plain `CREATE UNIQUE INDEX` takes a blocking lock on a live table and this repo has already documented that tradeoff (`migrations/20261118120000_user_phone_partial_unique/migration.sql:43-45`).
2. **Provider seam.** `stat`, `readStream` returning status and headers, `createUploadAuth`, signed reads for private objects, `LocalDiskStorage` implementation. No route changes; existing behaviour pinned by test.
3. **`sniffMime` narrowing.** Explicit brand allowlist to `video/mp4`, `qt  ` to `video/quicktime`, EBML to null, HEIC still a photo.
4. **`UnitUpdateSummary`** behind the existing call sites, with `lastPhotoStage` still populated. Photo-only behaviour unchanged, web typecheck green.
5. **Routes**: upload-auth, record, cancel, coded errors, `deletePhoto` handling both keys.
6. **Streaming**: the BFF regression suite first (JSON POST, 204, HEAD, PDF, 206 passthrough), then media streaming and Range forwarding.
7. **UI**: recorder, picker, playback, flag wrapper, and the removal of `lastPhotoStage` in the same commit as its last reader.
8. **WhatsApp**: `SiteUpdateDelivery` writes, deep-link send, status surface. The clip itself waits for the template.

### 11. Tests

- `sniffMime`: `qt  ` to `video/quicktime`, EBML to null, `isom`/`mp42` to `video/mp4`, HEIC still a photo.
- Schema: a VIDEO without poster, duration or size is rejected; with `archivedAt` it is accepted; duration 46s rejected; two rows cannot share `("organizationId","key")`; a null `key` is legal on an archived row.
- RLS: a non-member insert into `SiteUpdateDelivery` is denied; a cron claim succeeds only with both impersonation settings; `StorageUsage` is invisible to another organisation.
- Service: replay with matching keys returns the row; differing keys give 409 and delete nothing; a private-check failure deletes the object; a retryable insert failure deletes neither; deleting a video deletes two objects.
- Signing: HMAC over `token + expire`, 600 second expiry, folder equals `/<org>/<uploadId>/`.
- Streams: `Range: bytes=0-1023` returns 206 with the right `Content-Range`; a whole-file read returns 200 with `Accept-Ranges`; a bare CDN URL for a private object returns 403 while the same bytes come back through the BFF.
- BFF: JSON POST, 204, HEAD and PDF still work; media GET forwards `Range` upstream (assert on the upstream request, not only the response) and returns 206; a redirect is followed server-side and the browser never sees a Location.
- WhatsApp: template when the window is closed, freeform when open, `SKIPPED_WINDOW` when no template exists.
- End to end: record in a real browser from an MP4 fixture, see the tile, open the lightbox, seek and observe a 206; a MOV pick is refused with the right sentence; denied camera falls back; the portal plays through `/api/bff/media/...`; the phone-field spec stays green.

Fixtures are MP4, not WebM, because the pipeline refuses WebM by design. A three second clip and a `.mov` for the refusal case, checked in, plus a seed row so a cold clone opens every surface.

### 12. Retention, caps and counters

- Retention runs 24 months after an actual handover. No such field exists today: the only dates are `Unit.expectedHandoverDate` and `ProjectMilestone.completedAt`. Step 1 adds `Unit.handoverCompletedAt`, nullable, and nothing is purged while it is null.
- Purge is three phases, because clearing keys first would leave the cron unable to name the objects: set `archivedAt` (keys retained), delete the objects by key, then null the keys and record both in audit.
- The per-organisation cap is enforced at record time from the server-verified `sizeBytes`, not at signing time. A pre-signing check is advisory only, because a signed token allows repeated uploads inside its 600 second window with no server in the loop. `StorageUsage` is a reservation table, incremented on record, decremented on delete.
- Counters: `video.upload.started`, `video.upload.failed` with `code`, `video.playback.failed`. Log-only, stated rather than implied.
- Orphan sweep: daily, deletes objects inside a `/<org>/<uploadId>/` folder that no row references after 24 hours, poster included because it lives in the same folder.

### 16. Decisions

| Question          | Answer                                                                           | Why                                               |
| ----------------- | -------------------------------------------------------------------------------- | ------------------------------------------------- |
| One table or two  | one, `kind` discriminator                                                        | one timeline, one access rule, one delete path    |
| Audio             | visible per-clip toggle, default off                                             | owner decision; nothing blocks it later           |
| Duration          | 45s, DB CHECK, API and UI                                                        | matches the WhatsApp budget                       |
| Bytes             | 14MiB cap; 45s at 2.5 Mbps is 14.06 MB decimal, 13.4MiB, so the cap has headroom | one constant, one CHECK                           |
| Photos per note   | 8                                                                                | today's cap                                       |
| Videos per note   | 1, next update one tap away                                                      | keeps capture fast and the message small          |
| Video stage       | nullable, and the derived stage comes from the newest staged row                 | a clip may have no stage                          |
| Poster            | required unless archived                                                         | a blank tile is worse than a tombstone            |
| Client `mimeType` | not accepted                                                                     | bytes decide, as photos already do                |
| Clips             | private, verified server-side after upload                                       | interior footage; the flag is proven to work      |
| Container         | MP4 forced at the recorder, WebM refused                                         | Meta and the sniffer both refuse WebM             |
| WhatsApp v1       | deep link, clip after template approval                                          | removes a day of untestable work from the release |
| Retention         | 24 months after `handoverCompletedAt`                                            | an expected date is not a handover                |
| Flag              | `SITE_VIDEO_CAPTURE`, read by a server wrapper page                              | the capture page is a client component            |

Unresolved, and flagged as such: ImageKit's `Range` behaviour for private objects above 14MB is unmeasured and step 6 proves or changes it; Meta's video header ceiling is unverified and would move the byte cap down.

### 17. Not in scope

Public clips, WebM capture, transcoding, codec probing beyond the container, multiple clips per note, trimming and overlays, per-user quotas, Sentry or a dashboard, migrating existing photo objects, converting the photo routes' error shape, and Meta template approval itself.
